# KANS 高成本低ROI 素材预警 · Windows 版(精简)

和 Mac 版同一套扫描内核,但**精简掉了 Server酱手机推送和 Google 云盘上传** ——
**扫描结果直接输出到桌面**。适合放在那台 24h 常开的电脑上跑。

- 监控:6 个商品广告 + 2 个直播 GMV Max(共 8 个,见 `campaigns.json`)
- 命中:归一化成本 > ¥70 且 ROI < 2(直播 ROI 用页面自带的 ROI 列,和后台一致)
- 输出:**桌面\KANS高成本低ROI预警\<时间串>.xlsx**

- **全程只读**

1. 装 **Node.js LTS**:https://nodejs.org(装完**重启一下命令行/电脑**,否则可能找不到 node)
2. 把整个 `kans-roi-monitor-win` 文件夹拷到本机(建议放 `E:\kans-roi-monitor-win`,路径别带空格)

## 更新日志

### 2026-09-11 稳定性 + 多语言修复

针对反复出现的 `page.goto: Timeout 60000ms exceeded` 和「页面显示英文就不工作」。

**1. 导航不再一超时就废掉整轮**
- 等待条件从 `domcontentloaded`(要等一堆 JS/图片下完)改成 `commit`(服务器一回响应就算到位),
  再单独轮询等表格出现。这是超时率下降最主要的一条。
- 导航失败自动重试 3 次(退避 3s → 6s → …);报超时但其实已经跳到目标页的情况直接放行。
- 图片/字体/视频一律不下载(只读表格文字),首屏快很多。
- 任何一步失败都不再抛异常 —— 单个计划跳过,其余 7 个照常扫。

**2. 失败不再干等一小时**
- 失败后 6 分钟自动补跑一次(每小时最多补 2 次)。
- 偶发失败只写日志;**连续 2 轮**失败才推手机,消息也改成人话(不再贴一坨堆栈)。
- 同一时刻只允许一轮在跑,上一轮没完就跳过本次整点,避免叠加把浏览器拖死。

**3. 页面卡死自动重启浏览器**(登录没掉但页面不动的情况)
- 单轮内:首个页面打不开 / 白屏 / 页面 JS 无响应 / 连续 2 个计划失败 → 就地重启浏览器再继续。
- 单轮超过 40 分钟没跑完 → 强制结束并重启浏览器。
- 每连续跑满 12 轮主动重启一次(清 Chromium 长跑残留)。
- 修掉一个会挂死的坑:导航卡住时 `page.evaluate` 会无限期等下去(实测挂了 5 分钟以上),
  现在所有页面调用都有硬超时。

**4. 界面显示英文/越南语也能扫**
- 以前表头正则全写死中文(作品ID / 成本 / 账号),页面一显示英文就找不到表格,
  误报「表格始终未加载」。现在中 / English / Tiếng Việt 三种表头都认。
- **修掉一个会算错钱的 bug**:越南语界面千分位用点(`2.000.000 ₫`),
  旧解析会读成 `2` —— 差一百万倍,成本永远达不到阈值,等于漏报。现在按语言无关方式解析。
- 表格认不出来时,自动把页面上真实的表头写进日志(`logs\<日期>.log`),下次一眼能看出是什么语言。

**新增可调项(`config.json`,不填就用默认值):**
```
"browser": { "waitUntil": "commit", "gotoRetries": 3, "tableTimeoutMs": 60000, "blockHeavyResources": true }
"stability": {
  "roundTimeoutMinutes": 40,          // 单轮看门狗
  "retryDelayMinutes": 6,             // 失败后多久补跑
  "maxRetriesPerHour": 2,
  "alertAfterConsecutiveFailures": 2, // 连续几轮失败才推手机
  "restartBrowserEveryRounds": 12,    // 跑多少轮主动重启浏览器
  "maxBrowserRestartsPerRound": 1
}
```

### 2026-09-11 第二轮复查(在上面基础上继续)

**5. 找到一个更早就存在的性能坑:请求拦截把浏览器缓存关掉了**

直播口径要改写接口日期,靠的是 Playwright 的 `page.route`。实测(已写进自检 [10]):
**只要装了 route,Chromium 的 HTTP 缓存就整个失效** —— 同一页连开 3 次,不装 route 时
JS 只下载 1 次,装了要下载 3 次。而老代码把这个拦截**永久**装在页面上,
于是每小时、每个计划、每次导航都要把后台几 MB 的 JS 重新下一遍。
这多半才是 60 秒导航超时的最大推手,而且从第一版就存在。

改成**按需开关**:直播计划才开拦截(顺便屏蔽图片当补偿),商品计划关掉,让缓存正常工作。
8 个计划里 6 个是商品,从第二轮起基本秒开。

**6. 修掉"8 个计划绑死在一个单点上"**

登录探测原来固定拿第 1 个计划当探针,它偶发打不开 → 整轮 8 个计划全放弃。
改成逐个探路(默认最多试 3 个),有一个能打开就继续。

**7. 单轮软预算,别被看门狗砍光**

网络差时 16 次导航 × 每次重试 3 遍理论上能跑到 90 分钟,会被 40 分钟看门狗硬砍、什么都拿不到。
现在跑满 25 分钟(或连续 4 个计划失败)就自己收工,**已经扫到的部分照常出表**,剩下的下一轮补。

**8. 告警退避 + 恢复报平安**

- 「所有计划都失败」以前每轮直接推一条,完全绕过了"连续 2 轮才响"的闸门 —— 已并进统一闸门。
- 长时间断网时告警会退避:第 2 次响一下,之后每 6 次才再响一次(**连挂 20 轮总共只推 4 条**)。
- 浏览器重启同样退避(第 2 次 + 之后每 5 次),不再每 6 分钟重开一次。
- 恢复正常后自动推一条「已恢复」。
- 这套策略抽成了纯函数 `failurePolicy()`,自检里逐条验证,不是嘴上说。

**9. 列识别体检**

0 命中时自动检查"素材ID / 成本 / ROI或总收入"这几列有没有认出来。
认不出(界面换措辞/换语言)就报「本计划结果不可信」并把真实表头写进日志,
而不是静悄悄报 0 命中。

**10. 看门狗砍掉的那一轮不会再回来捣乱**

单轮超时后新一轮会开跑,老那一轮的残余任务靠轮次号自知作废,不会重复出表/重复推送。

**自检**:`node src/index.js selftest` —— **79 项**,不用登录。
除了单元测试,还包含两个**端到端**用例:拿假后台完整跑一轮 `runOnce`
(有命中/无命中/打不开各一个 → 验证出表、跳过、不互相拖垮),
以及"全部计划都打不开"时是否安静收敛。自检用临时目录,不会碰真实的命中历史和输出。

### 时间说明

`dailySummaryHour` 是**越南时间**。默认 9 = 越南 9 点 = **北京时间 10 点**。
想按北京时间早上 9 点发,把它改成 **8**。改完下一轮自动生效,不用重启。

### ⚠️ 日报数字的口径

成本/GMV 取自**创意表格**:优先读表格自带的「合计」行;没有合计行就把所有分页逐行累加。
所以这是**素材层合计**,不一定等于后台计划级的官方数字。
